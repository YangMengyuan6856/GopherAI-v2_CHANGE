# 阿里云百炼模型分层迁移与线上验证经验

日期：2026-09-19（Asia/Shanghai）
适用分支：`add_eico`

## 1. 背景

阿里云百炼部分旧模型进入迁移窗口。项目需要在不改变前端请求格式、知识库向量索引和已有评测数据结构的前提下，完成模型替换，并兼顾面试演示所需的回答质量、延迟和按量成本。

本次迁移采用“按任务分层”的策略：简单、确定性的路径使用快速模型；需要跨文档推理、故障分析或评测裁决的路径使用更强的模型；普通聊天继续沿用项目远端显式配置。模型名称集中在配置层解析，业务代码不直接散落模型名。

## 2. 最终模型分层

| 工作负载 | 模型 | 选择理由 |
| --- | --- | --- |
| 意图识别、快速 RAG | `qwen3.7-flash-2026-07-15` | 规则优先、任务边界清晰，降低延迟和按量消耗 |
| 深度 RAG、父块上下文重写 | `qwen3.8-flash` | 支持跨文档整合，保留更好的综合回答能力 |
| 动态多 Agent、RCA 故障分析 | `qwen3.7-plus-2026-05-26` | 用于候选原因分析、证据组织和多步推理，优先保证质量 |
| Judge 评测 | `qwen3.7-plus-2026-05-26` | 使用独立 Judge 配置，避免用快速回答模型直接裁决质量 |
| 普通聊天 | 远端显式配置 `qwen-plus` | 保留已有线上行为，避免无意改变通用对话入口 |
| 向量 Embedding | `text-embedding-v4` | 维度与向量空间保持不变，避免重新生成和迁移 Redis 向量索引 |

这里的“分层”不是所有场景都选择最低价格模型，而是在快速路径、知识综合路径和复杂推理路径之间做有意的质量/延迟/成本取舍。

## 3. 旧配置的兼容策略

远端 `config.toml` 保留原有结构和用户配置，不要求立即手工改写线上配置。代码在读取配置时会对旧的 `qwen-turbo`（以及旧环境变量覆盖）做透明迁移：

- 旧快速模型配置映射到当前快速模型；
- 未提供新增的 deep、reasoning、judge 字段时，由配置层按任务类型提供分层 fallback；
- 远端显式设置的普通聊天 `qwen-plus` 继续优先使用；
- Embedding 不参与这次替换，继续使用 `text-embedding-v4`，保证已有向量数据可复用。

这样做的目的，是让部署能够兼容现有容器和配置，避免把一次模型迁移变成配置格式、索引数据和前端接口的同时迁移。

## 4. Thinking 参数治理

`qwen3.8-flash` 等 Qwen3 模型默认可能开启较重的 thinking。对于意图分类、确定性 RAG 生成、查询改写和 Rerank，这些路径不需要开放式长推理，代码统一传递 `enable_thinking=false`，减少响应时间和输出不确定性。

动态多 Agent、RCA 故障分析和 Judge 评测保留 reasoning 能力，因为这些任务需要综合多条证据、形成候选假设或进行质量判断。该开关只在配置/请求构造层集中治理，不改变业务层的调用接口。

## 5. 线上验证与性能结果

首版迁移发布后，普通聊天和快速 RAG 可以正常返回，但深度 RAG 实测为 **40.88 秒**，其中 Rerank 在 **4002 毫秒**处超时并走了有界回退。分析确认主要原因是确定性路径仍携带了不必要的 thinking 开销。

随后对确定性 RAG/意图路径关闭 thinking，并保留 deep、reasoning 和 Judge 的模型层级。修复后的线上实测如下：

| 场景 | 修复后耗时 | 结果 |
| --- | ---: | --- |
| 深度 RAG | 8.90 秒 | 完成综合回答 |
| Rerank | 4298 毫秒 | 在新的有界预算内完成 |
| 快速 RAG | 1.38 秒 | 正常返回带证据回答 |
| 普通聊天 | 2.38 秒 | 正常返回 |
| 动态多 Agent | 约 72 秒 | Plus 完成 3 轮 Supervisor 调度、2 次有证据交接的子任务委派并主动收束 |

深度路径仍有明确超时和回退保护；若外部模型或网络异常，不会无限等待，也不会因为单个重排步骤失败而破坏整体服务。

动态协作实测先由 KnowledgeAgent 查得 `release.timeout_seconds=47`，再把证据交给 DiagnosticAgent 分析 HTTP 502 与 `context deadline exceeded`。最终结果明确区分“文档配置事实”和“待验证运行时假设”，没有把候选原因冒充已确认根因。

## 6. 按量计费与模型生命周期

本项目是低频面试演示环境，因此没有为了最低单价牺牲所有复杂任务的质量：高频、确定性链路使用 Flash，低频的动态多 Agent、RCA 和 Judge 使用 Plus。三个候选模型都支持按 Token 后付费，不要求购买包月套餐。

需要区分两件事：

- 新人免费额度到期或耗尽：额度不再抵扣，若账号未开启“额度用完即停”，请求会继续并转为按量计费；
- 模型正式下线：推理接口停止服务，即使愿意付费也不能继续调用，必须迁移模型。

公开政策中的新人额度与当前账号剩余额度不是同一个概念，后者以百炼控制台为准。当前选用的三个新模型仍在官方推荐模型目录中；迁移逻辑是为了避开短信所述的老旧模型下线风险。

## 8. 评测基线注意事项

迁移前的 Full/Judge 结果属于旧模型基线，不能直接当作新模型的效果结论。模型迁移改变了回答分布和可能的延迟，因此后续如果要对外宣称新的评测基线，需要在同一批评测用例上重新运行并重新校准 Judge，再比较相关性、完整性、有用性、证据一致性等指标。

已有历史报告仍然保留，用于回溯和对比；不能通过修改历史人工标签或直接沿用旧 K 值来宣称迁移后的质量提升。

## 9. 运维经验

- 线上 ECS 只负责运行容器，不在小内存服务器上编译；本地构建后再通过现有 SSH 上传和原子切换流程发布。
- 发布前保留上一版本和配置，健康门通过后再切换流量。
- 模型升级优先先做 direct API smoke，再做普通聊天、快速 RAG、深度 RAG 和复杂 Agent 的分层验证。
- 只在面向用户的真实推理任务中保留 reasoning；确定性流水线应显式限制思考预算，避免“模型能回答但接口超时”的假成功。
