# RCAEval 已知故障案例辅助排查规格

> 后续增量：用户于 2026-09-09 明确要求模型自主选择工具并基于新证据迭代推理。新实现见 [自主排查 Agent 规格](RCAEval-AUTONOMOUS-AGENT-SPEC.zh-CN.md)；本文保留为原确定性对照版本，不再代表新 Agent 的调度方式。

- 日期：2026-09-09；版本：v1.0（按已知故障范围完成首轮实现与留出评测）。
- 分支：`add_eico`；用户同意在主开发分支加入独立实验页。
- 状态：实现、本地留出评测、线上发布与浏览器验收完成；发布代码 `24e574f9`，详见同日 GlobalExperience。
- 当前目标：识别参考案例库已经覆盖的故障模式，并给出候选故障服务、原因、当前依据和待确认项。
- 不再要求：开放式发现未知故障、让大模型自由扩展根因类别、任意系统通用诊断、自动修复。

## 1. 任务定位

产品定位为“已知故障模式识别与案例辅助排查”。

面对给定的观测窗口，系统从有限的已支持故障模式中匹配和排序。当前证据通过门槛时，返回相似历史案例对应的候选服务与原因；未通过时返回“证据不足”。范围外故障也可能与已知模式相似，当前实现不能保证识别并拒绝所有范围外输入，必须单独报告误接纳率。

历史案例是参考，不是当前故障根因已被确认的证明。不能把最相似的一个案例无条件当成答案，也不能把不同故障恰好相同的某个指标峰值视为充分证明。

必须区分：

- 支持已知模式：例如历史上见过 checkoutservice 内存压力，能否识别该服务下一次同类故障。
- 复述原题答案：再次输入已存入参考库的同一次事故。这只能证明查询功能，不作为诊断成绩。
- 识别新型故障：首版不要求，不能宣传该能力。

## 2. 资源与现有框架

2026-09-09 只读 SSH 实测：2 vCPU、1612MiB 总内存、约 400MiB available、无 swap，根分区剩余约 12GB。部署前重新测量，不能把本次快照当永久余量。

保留现有规则诊断、案例检索、Harness、Tool Runtime、审计和鉴权。当前文本错误规则继续用于 Redis NOAUTH 等已有功能。

RCAEval 的输入是指标、日志和调用链，而不是一定含有错误码的短文本。因此首版补充“结构化观测 → 已知故障模式匹配”适配器，不重写为自由规划型多 Agent，不强行把 CPU 高等现象转换成错误码冒充命中旧规则。

原始 Parquet 在本地处理；ECS 只读取小型证据包和参考案例。模型若启用，使用已有云端模型调用，不在服务器运行大模型或完整演示微服务集群。

## 3. 支持范围与样本划分

来源：[RCAEval 官方数据卡](https://huggingface.co/datasets/phamquiluan/RCAEval)，MIT。
固定 revision：`afeacb11bcc94dadfd1c8f483ee4377b2b8b614e`。

先选 Online Boutique 的 RE2-OB。服务范围仅 checkoutservice、currencyservice；支持模式仅 CPU 压力、内存压力、网络延迟，共 6 个“服务 × 故障类型”已知组合。不宣传覆盖全部 RCAEval 或任何微服务系统。

| 分组 | 数量 | 选择规则 |
| --- | ---: | --- |
| 参考案例库 | 6 | 两个服务 × cpu/mem/delay，各取 repetition=1 |
| 开发集：范围内 | 6 | 同六个组合，各取 repetition=2 |
| 开发集：范围外 | 3 | checkoutservice/disk、currencyservice/loss、checkoutservice/socket，各取 repetition=2 |
| 留出集：范围内 | 6 | 同六个支持组合，各取 repetition=3 |
| 留出集：范围外 | 6 | 两个服务 × disk/loss/socket，各取 repetition=3 |

合计 27 个原始案例。其中留出集共 12 个，不能算作 12 个已知故障成功识别案例；范围内识别与范围外误接纳分别计分。

此前已查看过的 checkoutservice 的 cpu/mem/delay 三个样例属于参考库，不计入留出成绩。

相比 v0.1，本版有意改用“同服务、同故障类型、不同实验运行”的划分，以对应用户收窄后的已知故障目标。虽然实验运行不同，但注入配方可能高度相似，因此只证明同分布已知模式复现，不能宣称新故障、新服务或跨系统泛化。

冻结案例 ID、原文件 Hash 与分组，检查重复文件及重复观测。完全重复的输入不能同时作参考与测试；发生重复时说明原因并按预先记录的规则重选，不按诊断是否成功挑选样本。文件不重叠也不意味着消除了同配方实验的相似性局限。

开发集的范围外案例用于调拒答逻辑，但不会增加支持模式。测试时“范围内/外”真值只能由评分器读取，不能提前告诉匹配器。

## 4. 历史案例存什么

每个参考案例保存：

- 来源与案例版本：公开故障注入数据、非客户真实历史事故。
- 系统/服务、观测范围和数据质量说明。
- 服务级指标变化轮廓、有限日志样例和调用链延迟摘要（本版没有构建依赖图）。
- 官方标注的故障服务、类型。
- 典型支持证据与应当区别的相似现象。
- 可进行的只读验证，以及哪些结果会削弱该假设。
- 修复结果：原始数据没有提供实际修复验证时，必须为 unknown。

六个案例组成的是模拟历史参考库，不声称按事故发生时间实现了真实在线学习。为保持小实验隔离，本版将六条公开参考案例作为只读、版本化 JSON 嵌入程序，没有导入生产 MySQL 历史案例表；生产历史案例模块仍保持 MySQL 权威存储。线上工具审计写入已有 MySQL 表。使用小规模确定性相似度检索，不为六条记录新建向量数据库。

留出标签、原始编码答案的目录名、下载脚本和含答案说明不得被匹配器或大模型读取。参考库与留出评分器使用不同访问接口，不能只靠文件夹名称假定已经隔离。

## 5. 最小诊断链路

### A. 观测整理：确定性程序

本地读取全部服务的指标、日志和调用链，生成有界证据包。特征选取规则预先固定，不按故障标签挑选“正确服务”的证据。

指标保留 12 个分桶趋势点、窗口中位数、log2 变化量与缺失情况；日志保留频次、关键词计数与有限样例；调用链汇总服务级 p95 延迟、span 数与有限原始 span 引用。本版不做日志模板挖掘和拓扑因果推断。

reference/current 窗口根据输入范围按固定规则分段，不使用官方 inject_time 或根因标签给在线匹配器提示答案。参考段是否健康是一个显式假设，不稳定时显示警告；首版处理已经给定的事故窗口，不宣传故障时刻自动检测。

### B. 已知模式检索与匹配：确定性程序

从已支持模式中召回候选，以 CPU、内存、latency-90、socket、workload 五维指标轮廓及历史相似性排序。日志、调用链经真实工具补查后作为辅助材料，不参与本版排名。固定特征与权重在开发集上确定后冻结，不学习留出答案。

服务选择不等于全局最大指标选择。内存故障也可能伴随 CPU 上升；匹配需检查多特征一致性，并显示关键差异。

相似度只是排序分数，不是根因概率。达到最低证据要求且候选具有可解释支持，才输出候选；低匹配、明显冲突、证据缺失或多个候选无法区分时，允许“无法确认/超出范围”，不总是返回最近邻。

### C. 只读核验：受治理工具

使用已有 Tool Runtime 执行固定、有界的读取工作流：先读指标，再检索参考案例，最后补查日志和调用链。本版不让 LLM 自主选择工具或自由编写子任务。

- `rca_snapshot_metrics`：全部服务的窗口指标变化。
- `rca_snapshot_logs`：日志计数和样例。
- `rca_snapshot_traces`：服务级调用延迟、计数与 span 引用。
- `rca_reference_cases`：受限参考库的候选，不含测试答案。

工具只读取当前 benchmark 快照，不能访问真实生产主机。已有材料没有相应证据时显示缺失，不模拟一个成功的查询结果。

### D. 诊断报告：确定性模板，零 LLM 调用

确定性流程输出候选、引用与待确认项。本版不调用大模型，避免把解释流畅度混作诊断准确性。未来若增加大模型润色，应独立评测，不得新增未注册的根因类别、覆盖匹配结果、伪造引用或把未执行修复写成已成功。

首版不依赖开放式规划 Agent，也不强制运行 KnowledgeAgent + DiagnosticAgent。现有 KnowledgeAgent 以后可补充 runbook，但不是本轮排查能力验证的先决条件。

## 6. 输入输出与页面

公开 API 输入仅为匿名 `case_id` 和三种预注册 `strategy`；服务清单、窗口与证据包从服务器只读数据集中解析，不接受客户端提交正确答案或任意路径。
不能输入 fault、root_cause_service、编码答案的原目录名或评分器结论。

输出：

- 最可能的候选服务（最多 3 个）及已支持的候选故障类型。
- 当前支持证据和可获得的反证/差异，每条关联服务、时间和来源。
- 参考了哪个历史案例，以及为何类似、哪里不同。
- 还需要确认什么、通过哪个只读查询验证、怎样的结果支持/削弱假设。
- 匹配失败、超出范围、缺少证据、数据被截断等状态。
- 耗时、工具轨迹、策略版本；调用模型时记录实际模型与用量。

当前观测与历史参考必须分开显示；“已知模式匹配”与“根因已确认”必须分开。引用 ID 存在只能说明引用合法，不能自动证明因果推理正确。

新增独立的 RCAEval 实验页面，不堆进聊天页。支持选择样本、诊断、展开当前证据和历史参考、最后查看评分答案。标准答案仅在回答完成后由独立评分接口返回给用户，不回流到诊断上下文。

## 7. 资源与治理预算

资源约束及已测量结果：

- 首批本地原始数据预算 1GiB；实际 27 例、81 个 Parquet，共 277,840,487 bytes。
- 单次工具返回最多 1MiB，实验语料不超过 32MiB；实际全部观测 JSON 为 2,050,103 bytes，原始 Parquet 不部署到 ECS。聚合/采样规则版本化，显示警告与来源。
- ECS 同时诊断 1 例；单次最多 4 次只读工具调用，总超时 60 秒。
- 报告模型调用为 0，不产生模型 API 成本。
- 新能力目标增量峰值 RSS ≤100MiB；部署后主机 available 至少 256MiB，不满足则停用试验功能。
- 不新增常驻基础设施；不在 ECS 编译、运行 Pandas 批处理或做故障注入。

每个工具有 Schema、参数范围、授权数据集/案例范围、返回体大小、超时、审计。工具调用的 target 固定为 benchmark，不能将外部案例当作指令去修改 GopherAI 当前服务器。

## 8. 如何检验有效

不设定“必须做出高准确率”的结果；固定流程后保留全部成功、失败、拒答与错误案例。

对照：

| 组别 | 内容 | 作用 |
| --- | --- | --- |
| A | 当前文本规则诊断，接收相同观测摘要 | 留下改造前能力边界 |
| B | 已知故障特征规则匹配，不检索参考案例 | 判断仅加入观测适配能达到什么效果 |
| C | 同 B 的当前特征和资源优先规则，增加案例相似性、历史尺度自适应准入 | 判断这一组案例增强机制是否有增益；不是纯排序权重单变量消融 |

所有根因服务排名来自实际诊断，不来自格式化官方标签。B/C 使用相同当前观测与最多四次工具预算，B 实际读取三个当前观测工具，C 增加一次参考检索。案例增强同时影响准入和排序，不能将收益全部归因于某一因素。如果 C 没有改进，可以采用更简单的 B，不篡改结果。

主要指标：

- 范围内六例：根因服务 Top-1 / Top-3 命中数、故障类型命中数、服务与类型同时正确数、拒答/失败数。
- 范围外六例：被错误接纳为某个已知故障的数量、拒答数量；不能仅凭“输出一个泛泛候选”算通过。
- 所有案例：引用语法/归属有效性、少量人工抽查的证据支持情况、耗时、内存与模型成本。

在范围内案例上拒答也不能算正确；范围外是否成功拒答必须依据正式输出状态而非文字里有一句“仅供参考”。六例分母很小，展示具体分子/分母，不宣传统计上稳定的泛化准确率。

开发集用于定阈值与格式；留出集冻结后运行，不按结果微调再以原留出集宣称“未见测试”。使用模型时保留每次输出，不挑最好的结果。

官方标签可用于自动核对服务与故障类型。用户无需再标注几百道题，只需抽看 3～5 例的引用、待确认项和表述是否合理。

## 9. 修复有效性如何处理

本轮只证明排查能力，不承诺修复有效。RCAEval 的静态观测可以支持诊断判断，不能证明执行某命令后系统已经恢复。

可实际验证的治理：写操作/越权请求被拒绝；只读工具有界；取消/超时有效；调用有审计；工具结果真实可追溯。这些是治理能力，不是修复成功率。

修复建议最多标为 proposed / not_executed，说明前置条件、风险、预期恢复指标、回滚方式与所需审批。原始案例没有修复证据时，不填造成功解决办法。

未来若要验证实际修复，另在隔离环境选择少量可控故障，执行批准动作并测量恢复/副作用。不得在承载项目演示的唯一 ECS 上注入故障，也不能用内存模拟返回成功冒充真实修复。

## 10. 按最小闭环开发

1. 先用三个已下载参考样例做观测适配，跑通数据 → 证据 → 当前基线，验证资源与标签隔离。
2. 加六个已知模式/参考案例的匹配、只读核验、结构化报告与独立页面；模型润色可以后加，先让主链路可运行。
3. 在九个开发样例上调整后冻结，再运行十二个留出样例，交付具体结果和不支持范围。
4. 逐个功能完成本地构建、既有云端发布流程、运行验收与 GitHub 推送；保留旧诊断路径，不在实验完成前切换正式聊天路由。

不先开发新型规划器、通用多 Agent DSL、图数据库或自动修复平台。根据实测结果决定是否值得扩大支持故障集合。
