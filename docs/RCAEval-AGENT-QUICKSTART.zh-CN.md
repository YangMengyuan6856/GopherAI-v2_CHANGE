# 自主排查实验：怎样操作和解释

## 它在排查哪个系统？

不是当前阿里云上的 GopherAI。输入来自公开 RCAEval 的 Online Boutique 演示微服务系统；研究者注入故障并采集了指标、日志与调用链。本实验把采集结果压缩成可查询的只读快照，不会在你的 ECS 上制造故障。

历史库包含6次较早的参考运行，标有当时的故障服务与类型；当前窗口的官方答案由独立评分器保管，不告诉 Agent。模型需要自己选择查询，逐轮比较当前证据与历史模式。

## 一次演示

1. 工作台首页按 M-01 至 M-10 排列，点击最后的 **M-10 自主排查实验**。
2. 保持“原留出集回放”，任选一个案例。窗口编号只是数据记录编号，不是严重程度或预设答案。
3. 点击 **启动自主排查 Agent**。运行使用真实云端模型，可能需要1至3分钟；此时不要重复点或离开页面。
4. 结束后页面滚动到“排查结果”。查看每轮的简短假设、模型选择的工具及服务，再展开“本轮新返回证据”。下一轮实际收到的就是这些数据。
5. 查看最终排序候选、不确定性及尚未执行的核查建议，再展开标准答案核对。允许判断错误、证据不足或预算停止；这些都保留，不会换成规则答案。
6. 如需对比，在“规则对照”折叠区运行旧方案。规则版零模型调用，工具顺序固定，与上面的自主 Agent 是两条独立链路。

不想等待新调用时，可在“03 / 自主 Agent 真实模型回放”中展开逐例结果，点击“查看记录轨迹”。它读取已保存的实际运行，包含当时的失败；页面显著标明“记录回看”，不会伪装成实时执行，也不产生新模型费用。

右侧“仅切换下方数据展示”只切换你看到的服务曲线，不控制模型选哪个服务。模型每轮的工具和服务由自身决策，经 Go 治理校验后执行。

## 如何判断是否真的实现了 Agent？

看实际轨迹，不只看最后一段答案：

- 模型是否提出下一查询，工具是否真正执行并返回证据？
- 下一轮是否引用刚取得的数据、补充或削弱原有假设？
- 能否自行选择继续查询、检索历史案例或结束，而不是后端提前运行固定全套步骤？
- 是否记录真实模型调用次数、工具次数、Token、停止原因与引用？

不要求每轮改答案，也不要求不同案例必须走不同路径；强行展示变化同样是不真实的演示。本实验展示可核对的简短证据摘要，不展示模型的私有内部思维链。

## 三个指标不要混淆

| 观察 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 执行完成 | 模型在预算内形成符合结构及证据引用规则的结论 | 不代表诊断正确 |
| 服务与类型正确 | 这次输出与该案例官方标签一致 | 不代表新故障、生产系统也能正确 |
| 工具受治理 | 参数、权限、预算、重复调用与审计约束有效 | 不代表修复动作有效，当前不执行修复 |

当前只支持 checkoutservice、currencyservice 的 CPU、内存压力和网络延迟候选。磁盘、丢包、Socket 等范围外案例也会出现相似症状，模型可能误接纳；报告明确显示这些失败。

## 简洁的架构解释

一个模型负责有界的多轮诊断决策，Eino 接模型，Go Harness 管循环和预算，Tool Runtime 管只读查询、权限与审计。工具提供证据，模型比较并更新假设，独立评分器最后才核对答案。没有第三个模型裁判，也没有暗中读取答案或自动修复。

当前查询的是预先采集的观测快照，而不是持续增长的实时遥测。因此证明的是“基于新取得的证据进行迭代辅助排查”的实验能力，不是完整生产自动运维或因果根因确认。
