# 一、项目整体介绍类

## 1. 请你先整体介绍一下这个项目。

### 一句话回答
这是一个用 Go 实现的 AI 对话平台，支持多模型切换、RAG 检索增强、MCP 工具调用和 SSE 流式响应，并通过 RabbitMQ 异步持久化聊天消息。

### 展开回答
你可以从 4 层讲：

1. **模型层**：通过 `AIModel` 接口和工厂模式统一接入 OpenAI、Ollama、RAG 模型、MCP 工具模型。
2. **知识增强层**：支持上传文档做 embedding，写入 Redis 向量索引，聊天时做语义检索。
3. **工具调用层**：基于 MCP 协议接入工具，并在此基础上做了一个轻量级 Agent 技能。
4. **交互与持久化层**：前端通过 SSE 实时接收回答，后端把消息通过 RabbitMQ 异步写库。

### 可引用代码
- 聊天主链路：`service/session/session.go`
- 模型抽象：`common/aihelper/model.go`
- RAG：`common/rag/rag.go`
- Agent：`common/skill/builtin_agent.go`

### 加分说法
> 这个项目不是单纯调用某个模型 API，而是把模型能力、知识增强、工具调用和流式交互都做成了一个统一平台。

# 二、多模型抽象 / 工厂模式

## 3. 你为什么要抽象一个 AIModel 接口？

### 一句话回答
因为我不希望业务层直接依赖某个模型 SDK，而是希望把不同模型后端统一成同一套调用协议，降低耦合和维护成本。

### 展开回答
核心原因有 3 个：

1. **统一调用方式**：不管底层是 OpenAI、Ollama 还是带 RAG、MCP 能力的模型，上层都只调用统一接口。
2. **降低业务侵入**：controller 和 service 不需要写一堆 if-else 去区分不同模型。
3. **方便扩展**：后续新增模型时，只需要实现接口并注册到工厂，不需要改聊天主链路。

### 代码依据
- `common/aihelper/model.go:25`

### 面试延展
如果被问“接口里为什么要同时有流式和非流式”，可以答：

> 因为这两种能力都会被业务使用，如果拆成不同接口，调用层还得再做一次能力分发。统一放在 `AIModel` 里，上层更简单。

## 4. 你这个工厂模式具体是怎么实现的？

### 一句话回答
我用一个 `map[string]ModelCreator` 做注册表，`modelType` 作为 key，工厂根据 key 找到对应 creator 并创建模型实例。

### 展开回答
实现上主要有几个点：

1. 定义 `ModelCreator` 函数类型，表示“如何创建一个 AIModel”。
2. `AIModelFactory` 内部维护 `creators map[string]ModelCreator`。
3. 初始化时在 `registerCreators()` 里注册内置模型。
4. 调用方只传 `modelType` 和 config，工厂负责返回具体模型实例。

### 代码依据
- `common/aihelper/factory.go`

# 三、RAG / 检索增强生成

## 9. 你这个项目里的 RAG 是怎么做的？

### 一句话回答
用户上传文档后，系统用阿里百炼兼容 embedding 模型生成向量并写入 Redis Vector Search；聊天时再把用户问题向量化做 TopK 检索，把召回内容拼接进 prompt 后交给模型回答。

### 展开回答
完整链路是：

1. 上传 `.md` / `.txt` 文件
2. 保存到 `uploads/<username>`
3. 创建 embedding 模型
4. 在 Redis 中建立向量索引
5. 把文档写入索引
6. 聊天时取最后一条用户问题做语义检索
7. 将召回文档内容和用户问题一起拼进 prompt
8. 交给 `qwen-turbo` 生成回答

### 代码依据
- `service/file/file.go`
- `common/rag/rag.go`
- `common/aihelper/model.go:167`

---

## 10. 为什么说这里用的是阿里百炼 Embedding？

### 一句话回答
因为配置里用的是 DashScope 兼容接口、`text-embedding-v4` 作为 embedding 模型，chat 模型是 `qwen-turbo`。

### 展开回答
在 `config/config.toml` 里可以看到：

- `embeddingModel = "text-embedding-v4"`
- `chatModelName = "qwen-turbo"`
- `baseUrl = "https://dashscope.aliyuncs.com/compatible-mode/v1"`

这说明虽然代码封装用的是 OpenAI 兼容 client，但实际对接的是阿里 DashScope/百炼兼容接口。

### 代码依据
- `config/config.toml:38`

## 11. Redis Vector Search 是怎么落地的？

### 一句话回答
后端会在 Redis 中创建一个 RediSearch 向量索引，向量字段使用 `FLOAT32`，维度是 `1024`，距离度量采用 `COSINE`。

### 展开回答
`common/redis/redis.go` 中创建索引时定义了：

- `content`：文本字段
- `metadata`：元数据字段
- `vector`：向量字段
- `VECTOR FLAT`
- `TYPE FLOAT32`
- `DIM 1024`
- `DISTANCE_METRIC COSINE`

这些配置正是向量检索的底层实现依据。

### 代码依据
- `common/redis/redis.go:68`

## 12. 你为什么选择余弦相似度？

### 一句话回答
因为文本 embedding 场景下更常用余弦相似度来衡量语义方向是否接近，它对向量长度不敏感，更适合语义检索。

### 展开回答
你可以从两个角度回答：

1. **理论上**：embedding 更关注语义方向，cosine 更符合这种相似性判断。
2. **工程上**：主流向量检索系统和 embedding 模型搭配时，cosine 是很常见、很稳妥的选择。

### 面试提醒
不需要讲得过于数学化，除非面试官追问向量空间原理。

## 14. 那你为什么还能说自己做了 RAG？

### 一句话回答
因为 RAG 的核心闭环已经具备了：文档向量化、向量索引、语义检索、检索内容增强生成；只是当前粒度还比较粗。

### 展开回答
RAG 的关键不是一定要做到复杂 chunk 或 rerank，而是：

- 有没有外部知识载入
- 有没有向量化
- 有没有语义召回
- 有没有把召回结果回注到生成过程

当前项目这四步都有，所以可以称为轻量级 RAG 实现。

# 四、MCP / 工具调用 / Agent

## 18. 你为什么要引入 MCP？

### 一句话回答
因为 MCP 提供了统一的工具描述、工具发现和工具调用协议，适合把外部能力标准化接入到模型工具层。

### 展开回答
如果不用 MCP，常见做法是：

- 手写一堆内部函数调用约定
- 或者手写 HTTP API 描述给模型

这样会有两个问题：
- 工具接口描述不统一
- 后续新增工具时维护成本高

引入 MCP 后，工具就能以统一协议暴露，模型侧或 Agent 侧更容易做发现和调用。

3. **AgentSkill**：先动态发现工具，再让 LLM 生成调用计划，执行完后综合结果回答。

## 21. 你这个 Agent 的工作流是什么？

### 一句话回答
Agent 的核心流程是：工具发现 -> LLM 规划 -> 工具执行 -> 结果综合。

### 展开回答
具体 4 步：

1. **发现工具**：先通过 MCP `ListTools` 获取当前可用工具。
2. **智能规划**：把用户问题和工具列表交给 LLM，让它输出结构化 JSON 计划。
3. **批量执行**：后端按计划调用一个或多个 MCP Tool。
4. **结果综合**：把工具结果重新喂给 LLM，生成自然语言最终答案。

### 代码依据
- `common/skill/builtin_agent.go`

### 可直接复述的话
> 这个 Agent 不是让用户手工指定工具，而是由模型根据任务目标自主决定要不要用工具、用哪些工具，以及工具参数如何组织。

## 22. 你说的“两阶段调用机制”具体指什么？

### 一句话回答
第一阶段让模型做工具决策和调用规划，第二阶段在拿到真实工具结果后，再生成最终自然语言答案。

### 展开回答
这个项目里两阶段机制有两种体现：

1. **MCPModel**：先判断是否需要调工具，再根据工具结果生成答案。
2. **AgentSkill**：先生成工具计划，再基于执行结果综合回答。

这两个本质都是：
- 规划/决策阶段
- 结果生成阶段

### 代码依据
- `common/aihelper/model.go:371`
- `common/skill/builtin_agent.go:37`

---

## 23. 这里用的是原生 function calling 吗？

### 一句话回答
不是原生 provider-level function calling，而是通过 prompt 约束模型输出 JSON，再由后端解析执行。

### 展开回答
优点：
- 实现简单
- 模型兼容性更好
- 适合多模型平台

缺点：
- 更依赖 prompt 设计
- JSON 格式稳定性要额外关注
- 解析失败时需要做好兜底

### 高质量表达
> 所以我通常会把这个方案称为“prompt-based structured tool planning”，而不是原生函数调用。

## 27. Agent 规划质量受什么影响？

### 一句话回答

### 展开回答

1. 工具描述写得更清楚

4. 增加失败反馈后的重新规划
5. 对最终答案增加工具来源引用

## 28. 如果面试官问：你这里做 Agent 的意义是什么？

### 一句话回答
意义在于把“用户显式指定工具”升级成“模型根据任务目标自主决定是否用工具、如何组合工具”，提升系统的泛化处理能力。

### 展开回答
你可以从业务价值说：

- 降低用户对工具细节的认知负担
- 让工具能力更自然地融入问答流程
- 为后续扩展更多外部工具打基础

# 五、SSE / 流式输出 / 前端交互

## 29. 你为什么选 SSE，而不是 WebSocket？

### 一句话回答
因为当前核心需求是服务端单向持续推流，SSE 足够简单、实现成本更低，也更适合模型文本流式输出场景。

### 展开回答
SSE 的优点：

- 基于 HTTP，接入简单
- 浏览器支持好
- 很适合服务端单向推送文本流
- 不需要额外维护双向连接协议

如果场景变成：
- 双向实时协作
- 房间广播
- 多事件交互

那 WebSocket 会更合适。

---

## 30. 你这个 SSE 是怎么实现的？

### 一句话回答
后端在流式接口里设置 `text/event-stream` 响应头，并在模型每产出一个 chunk 时写入 `data: xxx\n\n`，然后立即 `Flush()` 到前端。

### 展开回答
关键点有 3 个：

1. 控制器设置 SSE 头部。
2. service 层定义回调，把模型输出写成 SSE 格式。
3. 每次写完调用 `http.Flusher.Flush()` 立即推送。

### 代码依据
- `controller/session/session.go:87`
- `service/session/session.go:103`

---

## 31. 前端是怎么消费这个流的？

### 一句话回答
前端没有直接用 `EventSource`，而是用 `fetch + ReadableStream` 手动解析 SSE `data:` 数据块。

### 展开回答
这样做的好处是：
- 更灵活
- 可以和当前业务请求结构更好融合
- 可以同时处理 `sessionId` 首帧、普通文本帧和 `[DONE]` 结束帧

### 代码依据
- `vue-frontend/src/views/AIChat.vue:368`

---

## 32. 你说“降低首字延迟”，这个代码依据是什么？

### 一句话回答
因为模型输出不是等全部生成后再返回，而是每生成一段就立即写给前端并 `Flush`，用户能更早看到首段内容。

### 展开回答
这里要注意说法：

- “降低首字延迟”是合理的工程判断
- 但如果没有压测和埋点，不要说成严格量化结论

### 高质量说法
> 这个优化主要提升的是用户感知时延，而不是我在当前仓库里已经做了严格 benchmark 的绝对性能指标。

---

## 33. 新建会话的流式接口为什么要先发 sessionId？

### 一句话回答
因为前端需要尽快知道当前流式消息属于哪个新会话，这样后续消息列表、会话列表和状态管理才能正确关联。

### 展开回答
这个设计的好处是：
- 不用等整条消息结束才拿到 sessionId
- 前端能更早完成会话状态初始化
- 用户体验更顺畅

### 代码依据
- `controller/session/session.go:103`

# 六、RabbitMQ / 异步持久化

## 34. RabbitMQ 在这个项目里解决了什么问题？

### 一句话回答
RabbitMQ 主要解决的是聊天消息写库对主响应链路的阻塞问题，把消息持久化异步化。

### 展开回答
原来如果直接同步写库：
- 每次用户消息、助手消息都要等待 DB insert
- 数据库抖动会拖慢聊天响应

现在改成：
- 主链路先发布消息到 MQ
- 消费者异步写 MySQL
- 用户更快看到模型回答

### 代码依据
- 发布：`common/aihelper/aihelper.go:29`
- 初始化：`common/rabbitmq/init.go`
- 消费写库：`common/rabbitmq/meesage.go`

---

## 35. RabbitMQ 这里是怎么工作的？

### 一句话回答
AIHelper 在保存消息时不直接写库，而是把消息序列化后投递到 `Message` 队列，由后台消费者读取后再写入 MySQL。

### 展开回答
流程可以这样说：

1. 用户消息进入会话
2. `saveFunc` 把消息包装成 MQ payload
3. 发布到 RabbitMQ
4. 消费者 goroutine 持续监听队列
5. 取到消息后反序列化
6. 调用 DAO 写数据库

---

## 36. 你这个 RabbitMQ 算是强可靠消息系统吗？

### 一句话回答
当前实现更偏异步解耦，不算强可靠消息系统。

### 展开回答
因为当前还缺一些典型可靠性机制：

- 队列不是 durable
- 消息没显式持久化
- 消费端 `autoAck=true`
- 没有 publisher confirm
- 没有失败重试和死信队列

### 高质量回答方式
> 所以这部分我会把它表述成“异步解耦和削峰”，而不会把它说成高可靠消息投递方案。

---

## 37. 那你为什么还说 RabbitMQ 提升了用户体验？

### 一句话回答
因为用户更在意先看到回答，而不是消息是否已经同步写入数据库；把写库从主链路拿掉后，感知响应会更好。

### 展开回答
要强调“体验”而不是“系统吞吐一定提升多少倍”。

一个比较稳妥的表达是：

> RabbitMQ 在这里的主要价值是把数据库写入从用户交互主链路里拆出去，让主链路更聚焦于生成和推送回答。

---

## 38. 会话创建也是异步的吗？

### 一句话回答
不是，会话创建当前还是同步写库。

### 展开回答
也就是说：
- **session** 创建：同步
- **message** 持久化：异步

这是个很适合体现你对系统边界理解的细节。

### 代码依据
- 会话写库：`service/session/session.go:70`
- 消息异步：`common/aihelper/aihelper.go:29`

---

## 39. 如果流式输出到一半服务挂了，会发生什么？

### 一句话回答
用户可能已经看到了部分 token，但最终 assistant 消息未必已经完整持久化，因为当前是在流结束后才把完整响应作为一条消息写入 MQ。

### 展开回答
这个回答会很加分，因为它体现你知道系统实际一致性边界。

你还可以补一句：

> 如果要增强这部分，一种方向是做流式阶段的中间状态记录或断点续传设计。

# 七、系统设计 / 工程意识类

## 40. 这个项目里你最认可的设计点是什么？

### 一句话回答
我最认可的是“能力分层”做得比较清楚：模型抽象、RAG、工具调用、流式输出和持久化是分层解耦的。

### 展开回答
例如：
- 模型抽象由 `AIModel` 负责
- 创建逻辑由工厂负责
- 会话编排由 `AIHelper` 负责
- RAG 独立在 `common/rag`
- MCP/Agent 独立在 `common/skill` 和 `common/mcp`
- 持久化异步化通过 MQ 处理

这使得后续扩展时改动范围更可控。

---

## 41. 你觉得当前实现最大的不足是什么？

### 一句话回答
我觉得最大的不足是几个关键能力已经打通了，但还处在“可用版”而不是“完全工程化版”。

### 展开回答
可以从 4 点讲：

1. **RAG**：还没有 chunk、overlap、rerank。
2. **Agent**：没有失败重规划、并行工具调度。
3. **MQ**：可靠性机制还比较弱。
4. **会话模型切换**：同一 session 里不是强热切换。

### 高质量表达
> 但我反而觉得这是一种真实的工程状态：先把核心闭环跑通，再逐步增强效果和可靠性。

---

## 42. 如果让你继续优化，你最优先做什么？

### 一句话回答
我会优先补三块：RAG 的 chunking、Agent 的失败重规划、MQ 的可靠性增强。

### 展开回答
#### 第一优先级：RAG
- 文本切块
- overlap
- 更细粒度 metadata
- rerank

#### 第二优先级：Agent
- 工具并行执行
- 错误分类
- 重规划机制
- 工具候选筛选

#### 第三优先级：MQ
- durable queue
- 手动 ack
- retry / DLQ
- publisher confirm

## 43. 你在这个项目里有没有做性能优化？

### 一句话回答
我更准确地说做的是“用户感知性能优化”和“链路解耦优化”，包括 SSE 流式输出、上下文 token 截断、消息异步持久化。

### 展开回答
- **SSE**：降低用户等待完整答案的时间
- **Token 截断**：避免上下文无限膨胀
- **MQ 异步写库**：减少数据库对主链路阻塞

### 注意点
不要随意讲精确性能数字，除非你手上真有压测数据。

## 44. 这个项目里有没有并发/线程安全方面需要注意的点？

3. **最后补 1 个代码位置或实现细节**
