# 原双 Agent 动态编排规格与验收

状态：已实现并上线（2026-09-10）；真实模型冒烟结果与局限见 GlobalExperience 对应发布记录。尚未完成动态版本的独立准确率评测，不沿用旧双 Agent 分数。

## 1. 目标与范围

仅升级原 `KnowledgeAgent + DiagnosticAgent` 协作入口，替换固定“规则规划 → 两路执行 → 合并”为模型驱动的“委派 → 证据反馈 → 再委派/停止”。RCAEval 自主单 Agent、其数据与历史成绩不改动。正式聊天、人工评分、策略活动指针不改动。

不声称未知故障泛化、实时主机排查或自动修复。旧双 Agent A/B 报告是固定流程的历史对照，不代表本版本的质量或收益。

## 2. 架构

- Supervisor：Eino ChatModel + 严格 JSON，生成具体 objective，选单角色或两角色同轮并行，通过 evidence_ids 选择已验证来源的交接证据。每轮返回子任务结果、状态与证据后再调用模型。
- KnowledgeAgent：按委派问题检索授权文档。交接内容仅作为检索线索，不插入知识库；仍经过现有证据门与引用校验。未 resolved 的兜底摘录不升级为成功知识结论。
- DiagnosticAgent：先用原始用户报告运行旧规则与历史建议，再由模型结合当前委派任务和授权交接证据形成待验证假设及待确认项。objective 绝不作为新的故障报告输入规则引擎。
- Go 合并器：保留各轮有引用的结果，检查权限、引用归属、ID 碰撞和结构化冲突，不充当因果裁判。引用正确不保证陈述语义或根因正确。
- 既有工具审计表保存 Supervisor 接受决策与各次委派结果的元数据和摘要 Hash；不保存明文请求、凭证或整份证据。完整轨迹随响应返回，可由用户下载，本版不提供断点恢复/历史轨迹 API。

## 3. 契约与预算

原 API `POST /api/v1/agent-runs/diagnostics/collaboration-shadow` 保持请求 `{message}`，增加返回 `orchestration`。公网前端经 `/api/agent-runs/...` 访问。

仅注册两个 worker 角色，Supervisor 不可创建新角色：

- 调度模型最多 5 次；累计委派最多 4 次；同轮最多并行 2 个不同角色。
- 总超时 180 秒；调度调用 30 秒；子任务 60 秒。取消通过 Go context 传播，依赖下游配合，不能强杀无视 context 的代码。
- Supervisor 单次上下文 64 KB、累计输入 200 KB；模型单响应配置 2000 tokens；子任务有次数及返回 Usage 门。Token Usage 是模型报告与执行后核对，不描述为可以预知账单的精确金额硬上限。
- 同角色、相同规范化 objective 与相同证据集合的重复委派被阻止；连续两轮无新增有效证据停止；重新取回相同来源不算新证据。
- 越权/伪造 evidence_ids、未知角色、额外 JSON 字段与超预算批次在执行前拒绝；非法模型输出最多允许再纠正一次。
- 一次仅允许运行一个协作请求，超出返回 429。审计失败停止后续派发，不静默回退旧流程。
- 子任务失败保留有效兄弟结果，显示部分完成；非正常预算/错误停止不能标成完整成功。

模型默认复用现有云端配置。若为百炼 qwen-turbo，仅该协作入口采用 qwen-plus，可由服务端 `GOPHERAI_COLLABORATION_MODEL` 覆盖。不向浏览器开放模型、URL、凭证或预算参数。

## 4. 前端

- `/dashboard/collaboration` 独立深色工作区，M-06 直达；M-10 RCA 顺序与功能不变。
- 输入问题后显式运行；示例只填输入，不偷偷消费模型额度。
- 完成后展示真实逐轮 objective、选择的 Agent、交接证据 ID、结果、失败与停止原因。
- 等待时仅显示实际用时，不演示预设假轨迹。支持取消请求、下载本次 JSON 记录。
- 原策略页保留旧规则规划与旧 A/B，折叠且明确不是动态版本成绩。

## 5. 自动验证

定向测试覆盖：模型跨轮重新委派、前轮证据交接、同轮真正并行、4 次总委派、保留早期结果、重复停止、未知角色/伪造引用、跨租户隔离、错误分支用量、取消、审计失败、诊断任务不能伪装成用户观察、未知诊断引用拒绝。

这些 stub 模型测试证明编排与治理契约，不是现实故障准确率。真实模型冒烟验证需要另外记录实际调度、成功/失败和资料前提；不反复重跑后只挑成功记录。

## 6. 人工验收

1. 从主页 M-06 打开动态协作，不应再看到所有工具在聊天页展开。
2. 点击“先查文档 → 再诊断”，保留默认示例并启动。前提是当前账号已有 `m3b-config.json`，其中 `release.timeout_seconds` 为 47。预期先检出该文档配置，再将返回的证据 ID 交给 DiagnosticAgent，分析模拟 HTTP 502 与 context deadline exceeded；必须区分文档值和现场状态，未确认的用途与原因列为待确认。若文档无对应内容，必须明确知识证据不足，不能造证据来完成交接。
3. 输入两个独立方向（例如核对 `m3b-config.json` 的 `release.timeout_seconds`，同时分析用户报告的 NOAUTH）。模型可同轮并行，也可选择串行；不要求每次次序完全相同。验收关注目标覆盖与任务结果，不以“恰好两个并行”充当智能标准。
4. 输入没有具体服务或日志的模糊问题，预期提出补充问题而不是确认故障或假装已执行命令。
5. 下载记录，确认有 trace、模型/版本/Prompt Hash、实际步骤和停止原因；旧 A/B 分数未被当作本轮成绩。

验收通过后，能证明的是有界动态多 Agent 编排链路可用，不自动获得生产切流、真实修复或诊断准确率提升结论。
