# GopherAI DevSupport：3～5 分钟中文面试演示

这份讲稿与页面顶部的 `🎤 面试导览` 一一对应。目标不是把所有工作台都展开，而是在 3～5 分钟内说明一个完整工程闭环，并让每个数字都能回到当前 Release、报告和 SHA-256 来源。

## 演示前准备

1. 登录在线页面，保留一个已有项目文档的账号。
2. 刷新页面，确认顶部存在 `面试导览`、`三级记忆`、`受治理工具`、`策略演算`、`评测总览`。
3. 点击 `面试导览`，确认顶部四张实时证据卡加载成功；若清理报告显示旧 Release，先到评测总览执行一次只读清理审计，再重新打开导览。
4. 不在面试现场执行服务器重启、生产写工具或真实故障注入；使用现有隔离报告和负向证据说明边界。

## 00:00～00:35：场景与安全切流

操作：保持导览第 1 步，点击“打开正式聊天”。输入一个项目知识问题，再观察回答下方的“实际路由”和“意图 Shadow”。

推荐表述：

> 这个项目服务研发知识问答和故障诊断。线上仍由固定 Policy Registry 决定实际路由；新的多策略意图识别先跑 Shadow，只记录候选意图和置信度，不自动切流。这样我能先比较准确率、延迟和误路由风险，再决定是否晋级。

应展示：

- 实际路由如 `legacy_chat · policy-v0` 或显式知识库开关触发的 `rag_fast · policy-rag-fast-v1`。
- Shadow 单独显示候选意图，并明确“不切流”。
- 两者不混成一行，也不把 Shadow 误讲成自主选模型。

高频追问：为什么不用一个 LLM 直接判断意图？

回答要点：规则/特征策略可解释且低延迟，模型策略覆盖长尾；Shadow 允许同请求比较而不承担线上风险。真正晋级需要固定数据集、混淆矩阵、成本与延迟共同达标，不只看单一准确率。

## 00:35～01:20：有依据的 RAG

操作：回到导览第 2 步，点击“打开证据检索”。选择已索引文档，输入一个跨 JSON/YAML 或部署文档问题，先运行混合检索，再基于证据回答。

推荐表述：

> 文档上传不是同步塞进 Prompt，而是 MySQL 记录权威版本和 Outbox，RabbitMQ Worker 异步解析与索引，Redis 保存向量和热数据。查询使用 Dense 与 BM25，经 RRF 融合后再次做用户和文档 ACL 校验；答案必须引用当前可访问版本，证据不足时拒答。

应展示：

- Chunk 的文档、版本、结构路径或行号引用。
- 版本 alias 与索引状态。
- 父子上下文只是候选策略，可单独 A/B；不是默认替换 `rag_fast`。
- 无可靠证据时页面明确“证据不足”，而不是让模型猜。

高频追问：为什么 MySQL、Redis、RabbitMQ 都要用？

回答要点：MySQL 保存不可丢的文档/任务/Run 状态，Redis 负责向量和短生命周期热数据，RabbitMQ 解耦索引计算并承接重试；三者职责不同。Redis 故障可以重建缓存，但不能丢失权威业务事实。

## 01:20～02:05：有界多 Agent

操作：回到导览第 3 步，点击“打开策略演算”。在“有限多 Agent 规划门”的输入框输入：

> 根据 m3b-config.json 核对发布配置，同时诊断后端 HTTP 502 和 Redis NOAUTH。

先点“只运行规划门”，确认候选为 `KnowledgeAgent + DiagnosticAgent`，再点“执行协作 Shadow”。

推荐表述：

> 系统不是默认多 Agent。只有知识核对与独立故障诊断同时存在、复杂度超过阈值时，规划门才允许最多两个 Agent 并行。它们各自有迭代、工具、Token 和总时限预算；合并器只接受带引用的结论，失败时显式降级到单 Agent，而且 Shadow 不影响下方正式聊天。

应展示：

- 复杂度、触发原因、Agent 上限和总超时。
- 两个 Agent 的独立状态、公开结论和引用。
- 部分失败时的降级原因，不能把降级显示成完整成功。

高频追问：Plan-and-Execute 与 ReAct 如何选择？

回答要点：固定诊断协议适合单 Agent 的短链路；只有可并行、证据边界清晰的复杂问题才先规划再执行。所有循环都有最大步数、重复动作指纹和 `NO_PROGRESS` 终止，不允许递归创建 Agent。

## 02:05～02:50：工具与三级记忆治理

操作：回到导览第 4 步，分别打开“受治理工具”和“三级记忆”。只查看已有报告与元数据，不执行生产写动作。

推荐表述：

> 工具不是把 MCP 名称直接暴露给模型。Registry 先检查版本、JSON Schema、权限、风险等级、超时、预算和幂等策略；Runtime 返回稳定的 ToolMessage，未知工具不会模糊匹配。记忆也按生命周期分层：Working 只服务当前 Run，Episodic 只保存用户确认的故障案例，Profile 保存稳定环境事实，并记录来源和过期时间。

应展示：

- 工具版本、参数 Schema、只读风险、预算和 ToolMessage 字段。
- retired demo 入口 24 小时调用为 0；计算器、时间、天气等弱场景工具不再作为亮点。
- 记忆装配的命中率、约束保留和 Token 预算；不要声称保存了隐藏思维链。

高频追问：如何避免 Agent 无限调用或产生副作用？

回答要点：最大工具数、相同 `tool + args_hash` 重复检测、请求取消传播、不可重试错误终止。v0.3 不开放 Shell/SQL 写/容器操作；唯一内部写动作也必须先生成 Proposal，再经人工确认、业务幂等键和事务 Outbox。

## 02:50～04:10：评测、观测与反馈闭环

操作：回到导览第 5 步，点击“打开评测总览”。依次指出 Full 320、固定阈值与 Z-score、策略建议、Harness Evolution 和面试证据包。

推荐表述：

> 我把评测和线上观测放在同一条证据链里。Prometheus 记录质量代理指标、延迟、错误和工具状态；固定阈值捕获确定性故障，滑动窗口 Z-score 捕获相对基线异常，但有最小样本、迟滞、冷却和变更预算。当前控制器只生成 Recommend-only 建议，不会直接写 active policy。候选必须经过离线成对比较、人工门、隔离 Shadow、Probe 和回滚约束。

应展示：

- Full 320 为数据目录完整性，不等同于 320 条人工评测已完成。
- 每个检测器同时显示固定阈值结果、Z-score 结果与低样本抑制原因。
- 当前 Harness 候选为负收益，被多重门禁拒绝，活动 Pointer 为 0。
- 证据包中的 Claim 有分子/分母、来源 Hash、版本关系、状态与禁止夸大边界。

高频追问：这算 Harness 自进化吗？

回答要点：这是受门控的离线演进框架，不是线上自改代码。Failure Miner 聚类失败，Proposer 只生成白名单单变量 Patch；Evolution/Validation/Sealed Holdout 隔离，比较时使用同 Case、同模型调用和同 Token 预算。当前候选负收益，因此被拒绝。能证明的是“坏候选不会进入生产”，不能宣称质量已提升。

## 04:10～04:40：收束

推荐收束：

> 这个项目的重点不是功能数量，而是把意图、RAG、Agent、工具、记忆、观测和评测连成一条可失败、可回退、可追溯的研发支持链路。当前 12 个面试 Claim 中 8 个达到技术证据门；最终质量结论仍被人工标签与 Judge 校准阻断。我会明确区分已实测、候选结果和规格目标。

## 不能说的表述

- 不说“Full 320 全部评测通过”；只能说数据目录 320/320 且 Hash/Schema 可复现。
- 不说“多 Agent 已提升质量”；当前仅证明受限协作和失败降级，多 Agent 的线上净收益门仍然严格。
- 不说“Harness 已自主进化成功”；当前自动候选是负收益并被拒绝。
- 不说“监控已经自动修改生产权重”；当前是 Recommend-only，Applied 为 0。
- 不说“支持任意 MCP/Skill”；Runtime 只接受 Registry 中通过治理的工具。
- 不说“已完成真实 5%～100% 生产灰度”；单实例环境不具备诚实验证条件。

## 演示故障时的恢复顺序

1. 页面证据卡加载失败：刷新后重试；不要把网络错误误报为证据不存在。
2. 清理报告与当前 Release 不一致：在评测总览运行一次清理审计，再重新打开面试导览。
3. RAG 无证据：确认文档版本已索引、当前账号有 ACL、问题指向真实文档内容；保留拒答作为正确安全语义。
4. 协作 Shadow 部分降级：展开结果说明哪个 Agent 缺证据或超预算；这是可演示的失败语义，不要隐藏。
5. 页面信息过长：使用顶部导航或面试导览的单步分页，不通过浏览器极限缩放展示整页。
